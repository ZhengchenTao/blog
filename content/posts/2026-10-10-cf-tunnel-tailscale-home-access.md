# 没有固定公网 IP，也能把家里的服务开到外网

说到把家里 NAS 上的服务开到外网，很多人的第一反应是：得先找运营商要固定公网 IP，域名还得备案，路由器上再开几个端口转发。

这个印象大概还停留在五六年前。我家现在的情况正好相反：

- 公网 IP 会变，今年 4 月到 7 月就变了三次；
- 入站 443 被运营商封了；
- 域名没有备案；
- 路由器对公网几乎不开端口（只有一个例外，后面说）。

博客、相册、记账、Git、WebDAV 这十几个服务，在外面照样能用。

整套做法可以用一句话概括：**网页服务走域名，经 Cloudflare Tunnel；SSH、数据库这类走 Tailscale。** 两条路都是家里主动往外连，外面的人不需要知道你家的 IP，更不需要它固定。

## 一、先看全貌

按“人在哪”和“连的是什么”分流：

| | 网页服务（博客、相册、记账、Git 网页） | SSH、数据库、Git over SSH |
|---|---|---|
| **在家** | 域名 → 路由器 DNS 指回 NAS → 反代 → 服务，不出家门 | 局域网 IP 直连 |
| **在外** | 域名 → Cloudflare 边缘 → Tunnel → NAS 反代 → 服务 | Tailscale → NAS |
| **例外** | 相册大文件上传：单独一个灰云域名，直连家宽 | — |

```
                        ┌──────────────── 在外 ────────────────┐
浏览器 / App ── 域名 ──►│ Cloudflare 边缘 ◄══ Tunnel（家里主动连出去）══╗
                        └───────────────────────────────────────┘          ║
                                                                            ▼
浏览器 / App ── 域名 ──► 路由器 DNS 指到 NAS ──────────────────────► NAS 反代 ──► 各服务
（在家）

终端 / 数据库客户端 ── Tailscale（点对点，或经中继）──────────────► NAS
```

这套分法给我两样东西：

- 同一个域名，在家在外都能打开，用的人不用关心自己在哪；
- SSH 和数据库端口不出现在任何公网入口上。

## 二、为什么不需要固定公网 IP

传统做法是这样的：域名 A 记录指向家宽 IP，路由器把端口转发到 NAS。这要求两件事同时成立：IP 不变，入站端口通。我家两条都不成立。IP 会漂，入站 443 在上游就被丢了。

Cloudflare Tunnel 的做法是反过来：NAS 上跑一个 `cloudflared`，由它主动连到 Cloudflare 边缘，维持几条长连接。用户的请求到了边缘以后，顺着这几条连接送回家里。DNS 里只有一条通配 CNAME，指向 `<tunnel-id>.cfargotunnel.com`，从头到尾不出现家宽 IP。

所以：

- 家宽 IP 变了，Tunnel 自己重连，外面无感；之前跟踪 IP 的 DDNS 脚本已经退役；
- 入站端口封不封都无所谓，路由器上那条端口转发也撤了；
- 新加一个服务，只需要在反代里加一个站点。通配 DNS 和通配证书都已经覆盖，DNS 和证书都不用碰。

我原来用的是“橙云 + Origin Rule 改写到 8443 回源”，结果整站三个月没被缓存。那次排查和迁移过程单独写过：[《Cloudflare 一直没缓存我的站，三个月后我才发现为什么》](/posts/cloudflare-8443-no-cache-tunnel/)。Tunnel 本身也有维护成本：协议要固定、出站别经代理、要防假活、要防 IPv4 断线。这些都补在那篇的更新段里，这里不重复。

## 三、为什么不用备案

备案是国内的接入商（云厂商、IDC）在接入环节要求的。这套架构里，域名解析到的是 Cloudflare 在海外的边缘节点，用户先连到海外，再顺着 Tunnel 回到家里，没有国内接入商这一环。

代价也在这里：Cloudflare 免费计划在国内没有节点，国内访客要先绕到海外边缘。我实测国内访问的首包时间在 0.6 秒上下，自己和家人用完全够。如果要面向国内大量用户，那是另一类需求，该老老实实上国内云、走备案。

## 四、橙云：IP 不暴露，代价是两条限制

Cloudflare 的“橙云”就是开代理。开了以后，公开 DNS 查到的是 Cloudflare 的 anycast 地址，扫描器拿不到家宽 IP；WAF、限速、爬虫拦截也都在边缘做。用 Tunnel 时子域名**只能**开橙云，CNAME 指向 `cfargotunnel.com` 的记录关不掉代理。

两条限制要心里有数：

1. **免费计划单个请求最大 100MB。** 打开网页、看图完全无感，但手机备份长视频会直接 413。
2. **非标准端口回源不缓存。** 走 Tunnel 以后没有“回源端口”的概念，这条自然就没了，前提是 Origin Rules 里别留着改写端口的规则（原因见上面那篇）。

顺带一个免费的优化：Smart Tiered Cache 在免费计划里也能开。开了以后，各地边缘没命中时先问上层节点，不必每次都回源。家宽上行通常只有几 Mbps，它才是真正的瓶颈，少回源一次就少占一次上行。

## 五、例外：相册上传为什么单独开了一个灰云域名

家人在外地，要用 Immich 备份手机照片。照片没问题，长视频动辄几百 MB，经 Cloudflare 一定 413。Immich 官方的分块上传 PR 今年 9 月被关掉了，没有合并，短期等不到官方方案。

能不能在原来的相册域名后面加个端口直连？不行。**DNS 记录里没有端口**，相册域名解析到的是 Cloudflare，加什么端口都会打到 Cloudflare。只能另起一个灰云名字，比如 `up.mydomain.com`，专门给上传用。

做法分四块：

| 环节 | 做法 |
|---|---|
| 端口 | 入站 443 被封，但高端口是通的，就用一个高端口。IPv4 在路由器上做端口转发；IPv6 在防火墙上只放 NAS 那一个地址的这一个端口，其余入站照旧全拒 |
| DNS | A 和 AAAA 同名，TTL 60。路由器上一个小脚本每 5 分钟只维护这一个名字。别去动那条通配记录，它是 Tunnel 的 CNAME，全站都靠它 |
| 反代 | 这个端口单独一个监听，**只认这一个 Host**，只转发到 Immich，其他 Host 一律断开；登录接口加限速。否则别人改一下 Host 头，就能从这个端口摸到反代后面的其他服务，绕开 Cloudflare 上的访问控制 |
| 证书 | 直连时浏览器和 App 看到的是源站证书。Cloudflare 的 Origin CA 证书只在“Cloudflare → 源站”这一跳有效，直连时谁都不认，所以要用公网 CA 签的证书。我用 Let's Encrypt 的 DNS-01 签了一张通配证书 |

还有个小坑：用户只敲域名加端口、不写 `https://` 时，浏览器默认按 http 访问，会得到一个 400 “Client sent an HTTP request to an HTTPS server”。在这个端口上加一条明文到 https 的跳转就行。

代价也要说清楚：家宽 IP 出现在了公开 DNS 里，会招来扫描和小流量的攻击；这条路也没有 Cloudflare 清洗。不过免费计划的 WAF 对应用本身的漏洞本来也只是有限防护，撞库则由反代上的登录限速兜住，所以多出来的风险主要在可用性。

我自己日常还是走橙云的相册域名，灰云这个只给家人上传用。原则是：**默认全部橙云，个别服务有硬需求再单独开灰云例外，不整站改灰云。**

## 六、在家：DNS 指回内网，流量不出家门

路由器同时是全屋的 DNS，它把 `*.mydomain.com` 直接解析到 NAS 的内网地址。于是同一个域名，在家走局域网，在外走 Cloudflare：

- 在家是局域网速度，没有 100MB 限制，也不占上行；
- 不用记两套地址，手机从 WiFi 切到 4G，App 里的地址不用改。

这也带来三个坑：

**1. 在家测不了外网链路。** 在家做的所有“外网验证”，其实测的都是内网。判断方法很简单：响应头里没有 `cf-ray`，就说明根本没经过 Cloudflare。外网验证一律从手机流量或境外机器发起。如果路由器上还有透明代理，连显式指定公共 DNS 的查询也可能被路由器接管，别拿家里的 `dig` 结果下结论。

**2. 偶发 `ERR_QUIC_PROTOCOL_ERROR`。** 在外访问时，Cloudflare 会通过 `Alt-Svc` 头告诉 Chrome“这个站支持 HTTP/3”，Chrome 会记住。回到家里，同一个域名解析到了 NAS，而家里的反代没开 UDP 443，QUIC 握手没有回应，就报这个错，刷新几次又好。解法是让内网反代回一个 `Alt-Svc: clear`，或者干脆也开 HTTP/3。

**3. 内网同样需要正经证书。** 在家直连时，浏览器看到的是源站证书，所以和第五节一样：Cloudflare 的 Origin CA 证书不行，得用公网 CA 签的。一张 Let's Encrypt 通配证书，内网、灰云直连、Tunnel 回源三处都能用。

## 七、Tailscale：SSH 和数据库

### 为什么不把它们也放到 Cloudflare

Cloudflare Tunnel 也能代理 SSH 和任意 TCP，但客户端要装 cloudflared 或者走 Access，数据库客户端用起来很别扭。我这里的分工很简单：HTTP 交给 Cloudflare，其余全交给 Tailscale。数据库端口不出现在任何公网入口上，只在 tailnet 里可见。

### 怎么连

- **SSH**：ssh config 里 `nas` 这个别名默认指向 tailnet IP。连之前探测一下局域网地址的 22 端口，能通就改用局域网 IP。在家在外都是同一条 `ssh nas`。
- **数据库**：客户端直接连 NAS 的 tailnet IP 加端口，不用 SSH 隧道。

这里有个很隐蔽的坑。群晖的 Tailscale 套件跑在 userspace 模式，没有 TUN 网卡，从 tailnet 进来的连接会被 tailscaled 转到 NAS 的 `127.0.0.1`。偏偏群晖自己的 PostgreSQL（相册、Drive 这些套件在用）就监听在 `127.0.0.1:5432`。于是连 `tailnet IP:5432` **能连上，但连的是群晖的系统库，不是我的容器**。静默连错库，比连不上更坑。我的解法是让容器另外发布一个端口，比如 15432，tailnet 上一律连这个。同理，容器端口如果只绑在局域网 IP 上，从 tailnet 也是连不到的。

也是因为 userspace 模式，我放弃了 Subnet Router 加 Split DNS（也就是让 tailnet 设备也用同一套域名）。那条路还会和路由器上的透明代理缠在一起，收益不值得长期维护。

### 三种连接方式

Tailscale 两端之间有三种走法，按优先级从高到低：

| 方式 | 是什么 | 体验 |
|---|---|---|
| **直连** | 两端用 STUN 问出各自的公网地址，再用 UDP 打洞 | 延迟约等于两地之间直连 |
| **Peer Relay** | 自己 tailnet 里一台有公网 IP 的机器当中继 | 延迟取决于中继放在哪，我用一台国内云服务器，十几毫秒 |
| **DERP** | Tailscale 官方中继，国内没有节点，最近的在香港、新加坡、东京 | 保证连得上，但延迟几百毫秒 |

打洞成功就不会走中继。看现在走的是哪种：

```bash
tailscale status          # 每个节点后面会写 direct / relay "sin" / peer-relay
tailscale ping nas        # 显示这次是 via 直连地址、via DERP 还是 via peer-relay
tailscale netcheck        # 看自己的公网出口和 NAT 类型
```

### 走了海外中继，先查梯子

这是我踩得最多的一类问题，结论是：**走了 DERP，大概率是代理工具的锅。**

原理是这样的：打洞前，Tailscale 要用 STUN 问一句“我的公网地址是什么”。如果 UDP 被透明代理或 TUN 模式带去了海外节点，问出来的就是代理的出口地址。对端按这个地址打洞，必然失败，只能退回 DERP。判断标准就是 `tailscale netcheck` 报的出口：**不是你家宽的 IP，就是这个问题。**

我家的实例：路由器上的透明代理把 NAS 的全部 UDP 都劫持了，netcheck 报的出口是新加坡的代理节点。云服务器连 NAS 只能走新加坡 DERP，延迟 350 到 800 毫秒。给 NAS 加了一条规则，让 UDP 不走代理（TCP 照旧），出口回到家宽，马上变成直连。电脑上开 Clash TUN 也是同一个症状。

但别为了直连去拆代理。NAS 上没有需要代理的 UDP 流量，放开没事；电脑不一样，很多本来要走代理的应用也在用 UDP（比如 QUIC）。我试过给电脑放开 UDP、只留 443 走代理，结果有的服务立刻用不了，当场回滚。这种情况该上 Peer Relay，不该硬改代理。

还有一种情况和梯子无关：网络本身是**对称型 NAT**，每换一个目的地址就换一个出口端口，打洞在原理上就不可能。公司网络、一部分移动网络是这样；电脑同时开着全局 VPN 加国内分流，导致 STUN 出口和实际数据出口不一致，效果也一样。这种情况直接上 Peer Relay：找一台有公网 IP 的国内云服务器，

```bash
sudo tailscale set --relay-server-port=<端口>
```

再在防火墙和安全组里放行这个 UDP 端口，最后在 Tailscale 的访问控制里加一条 grant，把 `tailscale.com/cap/relay` 授给需要的节点（旧式的 `acls` 全放行规则不含这个能力，不加就不生效）。我公司电脑到 NAS 的延迟，从走 DERP 的二百多毫秒降到了十几毫秒。

## 八、什么时候真的需要公网 IP

- **大文件上传**：就是第五节那种情况。但也只需要“有”公网 IP，不需要“固定”，DDNS 就能搞定；
- **对公众开放的非 HTTP 服务**，比如游戏服、邮件；
- **面向国内大量用户的网站**：这时候要的已经不是公网 IP，而是国内云和备案。

反过来说，如果运营商给的是大内网（CGNAT），连公网 IP 都没有，那只有第五节那条路走不通，其余全部照常（Tailscale 打洞会更难，但 Peer Relay 兜得住）。

## 九、照着做的清单

- [ ] 域名托管到 Cloudflare，一条通配 CNAME 指向 Tunnel，橙云
- [ ] `cloudflared` 固定 http2，它的出站流量别经过代理
- [ ] 路由器 DNS 把自家域名解析到内网反代，反代用公网 CA 签的通配证书
- [ ] 有大文件上传需求的服务，单独开一个灰云子域名，独立端口只认这一个 Host
- [ ] SSH、数据库走 Tailscale，不开任何公网端口
- [ ] Tailscale 走了 DERP，先看 `netcheck` 的出口；打洞真打不通，找一台国内云服务器做 Peer Relay

---

固定公网 IP 解决的其实是“外面怎么找到我家”。换个方向想就简单了：让家里主动连出去，外面只需要找到 Cloudflare，或者找到 tailnet 里的另一台设备。
